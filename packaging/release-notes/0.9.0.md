# Entra PIM Manager 0.9.0

**Add the delegated permission Azure Service Management → `user_impersonation` to your App
Registration and grant admin consent again — in every tenant — before you roll out this
update.** The app now reads and activates Azure resource roles through Azure Resource Manager,
which needs this permission next to the Graph scopes. With admin consent in place nothing changes
at sign-in.

**A tenant that has not consented is never prompted.** The background read asks for the Azure token
silently and stops there — no consent dialog appears, for broker and device-code accounts alike.
The tenant group says "Azure resource roles unavailable: This tenant has not consented…" while
directory roles and groups keep loading as before, and the app waits an hour before asking again.
Grant the consent; the rows appear on their own within the hour, right after a restart, or as soon
as you sign the account in again. A
prompt would not have helped: Azure Service Management needs admin consent in most tenants, and an
unanswered dialog would hold up every other account's sign-in while it sat there.

## New

- **PIM for Azure Resources.** Azure RBAC roles the account is eligible for — at management-group,
  subscription, resource-group or resource scope — appear in the list next to directory roles and
  groups, labelled "Azure resource role" with the scope underneath ("Subscription: Prod",
  "Resource group: rg-prod"). They activate through the same form: duration bounded by the role's
  PIM settings, justification and ticket fields as the settings demand, approval banner,
  Conditional Access authentication context. Active Azure roles show up with their countdown and
  deactivate from the same list. An eligibility inherited through a group is activated for the
  signed-in user, as the portal does.
- **Settings shows tenants, not two lists that point at each other.** "App Registration" and
  "Accounts" were one card each, and reading them meant joining them in your head. They are now a
  single **TENANTS** section: one card per tenant, the accounts signed into it nested inside, and
  the things every account in that tenant shares — the App Registration, the ticket system — one
  level up behind a gear, where they visibly belong to the tenant rather than to a row. "Add
  account" sits on the tenant card, so the "Sign in with" question is already answered by the time
  the sign-in opens. A tenant whose registration you removed keeps its card and says so, instead of
  taking its accounts off screen. Drag now reorders **tenants** rather than individual accounts, and
  the popup's grouping follows. One change to note: a tenant's id and cloud are its identity and are
  no longer editable in place — a mistyped tenant id is removed and added again.
- **A short alias per account.** Settings → ACCOUNTS has a rename button on every row: give an
  enrollment a name you can read ("EADM", "Admin") and the popup shows it instead of the UPN, which
  a 380 px window cuts off exactly where two admin accounts differ. Without an alias the UPN is now
  shortened in the middle rather than at the end, and the full value is a tooltip away. The alias is
  yours alone — it is stored locally, never sent anywhere, and the account row in Settings keeps
  showing the real UPN and tenant next to it. The activation form always names the account as Entra
  knows it.
- **A ticket system per tenant.** Settings → App Registrations has a "Ticket system"
  field: set "ServiceNow" once for a tenant and every activation that asks for a ticket
  starts with it filled in — you only type the number. It stays editable for the odd
  exception, applies immediately (no restart, unlike the registration fields), and an
  empty field simply means no prefill. **The ticket system is no longer mandatory**
  either: Microsoft's ticketing rule requires the number alone, so the app stops
  demanding more than the service does and omits the field when you leave it blank.
- **One line per Azure role instead of one per scope.** A role you are eligible for on
  more than one scope is now a single collapsible entry — "Owner · 12 scopes" — with the
  scopes inside it. For an infrastructure team eligible on every subscription of a large
  estate, that turns hundreds of rows into a handful. A collapsed entry still says how
  many of its scopes are active right now, and a search opens the ones that match.
- **The list opens folded, and each tenant separates its kinds.** A tenant now starts
  collapsed, and opening it shows four lines rather than everything at once: **Directory
  roles**, **Administrative units**, **Groups** and **Azure roles**, each with its
  count and each collapsible. For an infrastructure team eligible across a large estate
  that is the difference between a popup you scroll for a minute and one you read. A
  folded section still says how many of its entries are active right now, and a search
  opens whatever matches. Small tenants open their sections straight away — headers over
  five rows help nobody. The three levels now also *look* like three levels: a tenant
  reads larger than the sections under it, a section reads as a caption rather than as
  another row, and a hairline down the left says where a tenant's entries end. A
  collapsed tenant carries the same green "n active" badge its sections do.
- **Pin what you use, and the last three come back on their own.** The pin on any row
  lifts it to a PINNED section at the top of the list; under it, RECENT holds the last
  three activations. Both carry their tenant and scope, both disappear while you search,
  and both quietly drop entries whose eligibility is gone.
- **Search covers everything the row shows.** Role name, type, tenant and, for Azure roles,
  the scope. With an eligibility on every subscription of a large estate, typing a subscription name is the
  only practical way to find one; "azure", "group" or "directory" now work as type filters too.
- **Active Azure roles show their scope.** The card drops the redundant "Azure resource role" so
  "Subscription: pl-mgmt" fits, and its tooltip carries the full ARM scope path. The
  expiry warning names it too — with Owner active on three subscriptions, "Owner expires
  in 1m" is not an answer.
- **A "What's new" window after an update.** The first start on a new version summarises
  what changed, once — one line per entry, with the full text a click away on GitHub — so a
  change that needs an admin action (like the permission at the top of these notes) is not
  something you find out from a warning line later. It ships with the build, so it works
  offline, and it stays away on an ordinary restart.
- **The network check covers Azure Resource Manager.** It probes
  `management.azure.com` (or the China host) as its own row.

## Fixed

- **A directory role limited to an administrative unit is finally visible as one.** It
  gets its own section and names the unit on the row, instead of looking exactly like the
  tenant-wide role of the same name. The unit is identified by its object id; resolving
  its display name would need a directory permission the app deliberately does not ask
  for.
- **The role-assignable warning moved to where you commit.** Joining a group that can carry
  directory roles may grant far more than group membership. That used to be a small badge in
  the list, read while browsing if at all — and missing entirely on a pinned row, the fastest
  way to activate. It is now a banner in the activation form, next to the approval and
  step-up ones, and it names the consequence rather than Microsoft's term for it.
- **"The request timed out" no longer stands in for "nobody consented".** A tenant without the
  Azure permission used to report a timeout, which reads as a network fault and sends you looking
  in the wrong place. The app now names the missing consent instead, and no longer opens the
  background sign-in prompt that produced the timeout. Tenants also get more time before a slow
  read counts as failed (30 s per account, 25 s for the Azure part): listing every scope of a
  large estate takes more than the previous budget allowed — and a read that does run out of time
  is simply tried again on the next refresh, instead of taking the Azure rows away for an hour.
- **The log stopped burying itself.** MSAL repeats a handful of warnings about its own
  environment on every token acquisition; with the 60-second refresh that was twelve lines a
  minute — a field log came back at 6.5 MB for half a day, 99.6 % of it those repeats, with
  everything worth reading buried in between. Each distinct message is now logged once per
  process instead of once per call. Nothing is suppressed and errors are never held back.
- **The what's-new window no longer depends on the version number alone.** Reinstalling the
  same build, or installing an older one and then the current one again, left it away: the
  recorded version had not changed, and settings survive both. It now also reacts to the
  installer having run, so it appears on a manual update, an automatic one, and a reinstall.
- **A missing consent is named on the tenant group.** It replaces the generic
  "Couldn't load eligibilities" — for the Azure rows, and for device-code accounts
  (`AADSTS65001`).

## Notes

- There is no pre-check ("Validate") for Azure resource roles: Azure Resource Manager has no
  dry-run, so the button is hidden for them and Azure validates the request on activation.
- Microsoft's 5-minute minimum active duration applies: the stop button stays disabled for five
  minutes after an Azure activation, as it does for directory roles.
- Activating at a narrower scope than the eligibility (one resource group of a subscription you
  are eligible on) is not offered; the role activates at the eligibility's own scope.
- An Azure role you are eligible for **through a group** appears like any other — but a group
  membership you changed minutes ago does not: Azure resolves memberships from its own cache, so a
  role inherited through a group you just joined can take a while to show up. Nothing to do but
  refresh again later; the app asks Azure again on every refresh.
- Entra China (21Vianet) uses `management.chinacloudapi.cn`; the Azure path there is untested.
- The full permission list is in `docs/app-registration-setup.md`; the per-tenant consent URL for
  a multi-tenant registration is in the same file and covers the new permission too.
