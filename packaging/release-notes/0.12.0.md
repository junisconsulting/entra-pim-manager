# Entra PIM Manager 0.12.0

A ready-made Intune app, and an unattended install that finally starts at logon.

## New

- **An Intune package with every release.** Next to the installer, each release now carries
  `Entra-PIM-Manager-win-Setup.intunewin`: the same installer, packed as a Win32 app together with
  the install and uninstall scripts. Upload it to Intune, paste the install command with your
  tenant and client id, set the detection rule, and assign it to users. It contains no tenant
  data, so the same file works for every tenant. The values to enter — and why "greater than or
  equal" is the only safe detection rule for an app that updates itself — are in
  [docs/unattended-deployment.md](https://github.com/junisconsulting/entra-pim-manager/blob/main/docs/unattended-deployment.md).
- **The install script runs on Windows PowerShell 5.1.** It used to require PowerShell 7, which no
  endpoint has out of the box, and which Intune's `powershell.exe` is not.

## Changed

- **Removing sits in the editor now, and asks twice.** The red X on a tenant card looked like
  "cancel" next to an open configuration — and removed the tenant's App Registration with one
  click. It is gone. The configuration has **Cancel** next to **Save**, and **Remove tenant** on the
  left, which now removes the tenant completely: its accounts with their sign-ins, its App
  Registration and its ticket system. An account is removed the same way, from its pencil. Both
  buttons ask for a second click within five seconds. Roles that are active stay active until they
  expire.

## Fixed

- **The tenant id in Settings → TENANTS can be selected and copied.** The gear on a tenant card
  showed it as plain text you could not even mark — awkward exactly when you need it for a
  deployment command.

- **A silent install now turns on autostart.** `Setup.exe --silent` — the way every script or
  Intune rollout installs — never starts the app, and autostart used to be switched on only at that
  first start. So an unattended install left the app installed and configured, but it never came
  up at the next logon. The installer now sets the entry itself, silent or not. The flip side: an
  install over an existing one — a repair, or the script run again — turns autostart back on, even
  for a user who had switched it off. An install made silently with 0.10.0 or 0.11.0 keeps its
  missing entry through this update: run the install again, or turn on **Start with Windows** under
  **Settings → Behavior**.
